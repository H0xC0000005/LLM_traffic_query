# Experiment launchers

These launchers call the existing experiment scripts with explicit configurations.
They do not change experiment source, algorithms, feature call signatures, or
prompt templates. Numeric settings in the supplied configs are editable recipes;
the old VS Code entries were mutable working configurations, not a frozen record
of every paper run.

The root `launch_ppo_run_new.ps1` and `launch_ppo_eval.ps1` are the new wrappers.
The originals are preserved for reference as
[`launch_ppo_run_new_legacy.ps1`](archive/launch_ppo_run_new_legacy.ps1) and
[`launch_ppo_eval_legacy.ps1`](archive/launch_ppo_eval_legacy.ps1), retaining their
pre-refactor behavior and settings.

## Start with a plan

Run these commands from the repository root in PowerShell. The launcher Python
needs PyYAML; each child uses its separately selected experiment interpreter.

```powershell
$launchPython = 'E:\anaconda3\envs\llm\python.exe'
Copy-Item launchers/configs/local.example.yaml launchers/configs/local.yaml
& $launchPython -m launchers.run --config launchers/configs/prompting.yaml --local launchers/configs/local.yaml --list
& $launchPython -m launchers.run --config launchers/configs/prompting.yaml --local launchers/configs/local.yaml --select energy-phase12 --plan
```

`--plan` is the default. It resolves matrices, arguments, dependencies, input
paths, and output declarations without starting experiment processes, importing
experiment modules, generating features, or writing run directories. It checks
argument names statically and reports missing inputs. It does **not** validate
the experiment's behavior, data schema, extractor compatibility, or numerical
results. `--list` prints expanded job IDs and stages.

Execution requires `--run` explicitly. For example, after reviewing the plan:

```powershell
& $launchPython -m launchers.run --config launchers/configs/prompting.yaml --local launchers/configs/local.yaml --select energy-phase12 --run
```

Credentials come from the launching shell. Prompting uses `OPENAI_API_KEY`;
the existing LLM-FE code requires `API_KEY` (the launcher supplies the inherited
`OPENAI_API_KEY` under that name when necessary). The launcher does not automatically
load the repository's `.env` file. Keep credentials out of YAML and arguments.

## Supplied configurations

| Config | Jobs and coverage |
| --- | --- |
| `prompting.yaml` | `energy-phase12`; `tsc-main-phase12-*`, `tsc-single-phase12-*`, `tsc-nonorm-phase12-*` over four scenarios; standalone `phase3-correction`. All use existing `--non-interactive` behavior. |
| `energy.yaml` | Six independent CV jobs: `energy-none`, `energy-expert`, `energy-rank2`, `energy-rank4`, `energy-rank5`, `energy-rank25`. Each runs the existing four-fold loop. Prepared Parquet data is required. |
| `tsc.yaml` | `tsc-train-<scenario>-<method>` and `tsc-eval-<scenario>-<method>`: 80 PPO trainings plus 92 evaluations, including rule controllers and both ablations. |
| `tsc_existing_eval.yaml` | One `tsc-existing-eval` job for an existing checkpoint; no training dependency. Supply `checkpoint`, optional `meta`, and the matching expert `extractor` when applicable. |
| `llmfe.yaml` | `llmfe-gpt-3.5-turbo`, `llmfe-gpt-4.1-mini`, `llmfe-gpt-5.4-mini`: candidate searches only, using the existing energy LLM-FE runner. |

TSC scenario IDs are `22L22L`, `2L3S23O`, `3232sk`, and `3LR23LR2`.
Main methods are `brp`, `brq`, `bu`, `erp`, `erq`, `eu`, `lb-a/t/f/p`,
`lo-a/t/f/p`, `ft`, `fa`, and `mp`. Ablations are `sa_p/q/u` and `ns_p/q/u`.
The last two groups select feature versions generated by the corresponding
ablation; they are not inference-time feature-zeroing switches.

Examples below only print plans:

```powershell
& $launchPython -m launchers.run --config launchers/configs/energy.yaml --local launchers/configs/local.yaml --select 'energy-*' --plan
& $launchPython -m launchers.run --config launchers/configs/tsc.yaml --local launchers/configs/local.yaml --select tsc-eval-22L22L-eu --plan
& $launchPython -m launchers.run --config launchers/configs/tsc.yaml --local launchers/configs/local.yaml --select 'tsc-eval-*-sa_*' --plan
& $launchPython -m launchers.run --config launchers/configs/llmfe.yaml --local launchers/configs/local.yaml --select llmfe-gpt-4.1-mini --plan
```

`--select` accepts job-ID wildcards and may be repeated. Selecting an evaluation
job also selects its training dependency automatically. These are jobs in a new
run, so selecting an evaluation does not reuse a previous run's checkpoint.
Rule-controller evaluations have no training dependency. No selection means all
jobs in that config; use a selection for a focused run.

For an existing checkpoint, use `tsc_existing_eval.yaml` instead of the matrix's
train/evaluate pair. For an expert checkpoint, provide the exact compatible
extractor through local variables, for example:

```yaml
variables:
  checkpoint: 'E:/runs/model.pt'
  extractor:
    path: 'E:/runs/inputs/extractor.py'
    symbol: tsc_isolated_intersection_feature_vector
```

Planning warns, and execution stops, if a checkpoint's sidecar identifies an
expert add-on but no extractor was selected. The sidecar is recorded with the
inputs. This does not infer that an arbitrary selected extractor is semantically
compatible; the version still needs to match the checkpoint.

`--jobs` sets the maximum concurrent child processes and defaults to `1`. Increase
it only to fit the available GPU memory, CPU/RAM, and API budget; the scheduler
does not allocate those resources. For example, append `--jobs 2 --run` after
reviewing the selected plan. Dependent jobs still wait for their inputs, and a
failed parent blocks its dependent jobs.

PowerShell entry points call the same launcher. Set
`EXPERIMENT_LAUNCHER_PYTHON` or pass `-PythonExe` to select the launcher runtime:

```powershell
.\launch_experiment.ps1 -Config energy -Select energy-expert -PythonExe $launchPython
.\launch_ppo_run_new.ps1 -Select tsc-train-22L22L-bu -PythonExe $launchPython
.\launch_ppo_eval.ps1 -Checkpoint 'E:/runs/model.pt' -ExtractorPath 'E:/runs/inputs/extractor.py' -PythonExe $launchPython
```

These wrappers plan by default; `-Run` executes. The generic wrapper automatically
uses `launchers/configs/local.yaml` when present. The new VS Code entries
**Experiment launcher: plan** and **Experiment launcher: run selected** likewise
use that local configuration and prompt for a config and job selection. Old
debug entries remain available. The legacy expert-feature flag is omitted.

## Settings and feature selection

`--local` deep-merges a machine-specific YAML mapping into the config. Put machine
paths in `configs/local.yaml`, starting from `local.example.yaml`. Mapping values
merge recursively; lists, including `jobs`, are replaced as a whole. `--var`
overrides a top-level variable and may be repeated; values are JSON scalars or
plain text. Use `--local` for nested settings.

```powershell
& $launchPython -m launchers.run --config launchers/configs/tsc.yaml --local launchers/configs/local.yaml --select tsc-train-22L22L-eu --var training_profile=current_launcher50 --var device=cpu --plan
& $launchPython -m launchers.run --config launchers/configs/energy.yaml --local launchers/configs/local.yaml --select energy-expert --var 'expert_extractor=E:/features/energy_extractor.py' --plan
```

Without interpreter overrides, child interpreters default to the launcher Python.
The local example selects the existing `sumo`, `energy_pred`, `llm`, and `llmfe`
environments and `E:/Sumo`. `SUMO_HOME` is supplied to TSC children.

Expert jobs snapshot their explicitly selected extractor, plus its mapping when
available. A child-only lazy import finder supplies that snapshot when unchanged
experiment code naturally imports `expert_feature_extractor`. It preserves the
original import order and call sites and does not replace a source file in the
repository. TSC evaluation receives the training job's same extractor snapshot.

The selected module must already implement the callable and data/schema contract
expected by the downstream script. The launcher checks a declared function name
statically; it does not adapt generated signatures, data columns, return layouts,
or caches. Newly generated energy extractors may still require manual integration.

For a regenerated TSC representation, override `variables.extractors` in the
local config, choosing the matching scenario and `full`, `single_agent`, or
`nonorm` variant:

```yaml
variables:
  extractors:
    22L22L:
      full:
        path: 'E:/features/corrected_tsc.py'
        mapping: 'E:/features/expert_feature_mapping.yaml'
        symbol: tsc_isolated_intersection_feature_vector
```

The shipped config selects saved local versions. Some prompting runs and maps
are ignored or external, so a fresh Git checkout may lack these inputs. A
mapping must belong to the selected code revision; do not substitute a mapping
from another run.

## Statistical correction remains an explicit handoff

Phase 1+2 writes an extractor and mapping. Run downstream diagnostics with that
version, then select the exact expert/baseline distribution CSVs and matching
task variables for `phase3-correction`. The launcher does not choose a latest CSV
or infer which representation a report describes.

```powershell
& $launchPython -m launchers.run --config launchers/configs/prompting.yaml --local launchers/configs/local.yaml --select phase3-correction --var 'phase12_run_dir=E:/runs/phase12/result' --var 'expert_stats_csv=E:/reports/expert.csv' --var 'baseline_stats_csv=E:/reports/baseline.csv' --var 'phase3_task_vars=E:/runs/phase12/inputs/task_vars.yaml' --var 'baseline_feature_description=E:/features/baseline_semantics.yaml' --plan
```

The `__SET_...` defaults allow planning but prevent executing phase 3 until the
inputs are supplied. TSC's baseline description is available in
`tests/auto_prompting/templates/tsc_scene_encoder_feature_blocks_semantics.yaml`.
Use matching energy semantics for energy correction. The complete energy
distribution-report handoff has not been added. Main/single-agent features retain
the correction step; no-normalization features skip it and use the dedicated
ablation prompts. Install/select the corrected version before final verification.

LLM-FE's frozen-candidate final evaluation has not been added either. Its search
jobs do not by themselves reproduce the paper's final fourth-fold comparison.

## Configuration and run records

Configs use `version: 1`, an arbitrary `variables` mapping, optional shared
`defaults`, and a `jobs` list. A job declares `id`, `stage`, `script`, optional
`python`/`cwd`/`env`, and an `args` mapping. Boolean `true` emits a flag;
`false`/`null` omits it; a scalar emits a flag/value pair. A `matrix` expands the
Cartesian product of its list-valued dimensions.

`${repo}`, `${run_dir}`, `${job_dir}`, interpreter variables, and matrix values
can appear in strings. Nested lookups such as `${scenarios.${scenario}.tls_id}`
select scenario-specific values. `inputs` lists files/directories to record;
`outputs` maps artifact names to `{path: ...}` or `{glob: ..., one: true}`.
Outputs are required unless `required: false`. Artifact references such as
`{from_job: tsc-train-22L22L-eu, artifact: checkpoint}` resolve after the producer
completes and create a dependency automatically. `depends_on` can add an explicit
dependency.

Plans show the actual child-wrapper `command`, its `entry_spec`, and the underlying
`experiment_command`. Running the latter directly bypasses extractor selection.
`wall_timeout_seconds` bounds a child process tree; a timeout records failure and
keeps any partial experiment outputs for inspection. It does not constitute a
successful scientific result. Ctrl+C stops active child process trees.

`yaml_inputs` declares a source YAML and overrides to materialize beneath the
job's input directory. Prompting uses this to substitute only the selected
scenario in a per-run task configuration; original templates remain unchanged.

Actual runs create a unique directory under `launch_runs/` by default; change
this with `--output-root`. The directory contains the resolved plan, original
config snapshot, aggregate status, and one directory per job. Job records include
`resolved.json`, `status.json`, `stdout.log`, `stderr.log`, successful
`artifacts.json`, and snapshots/hashes of file inputs. Directory inputs record
their paths rather than copying whole datasets. Local config provenance is
recorded without copying the local file; environment values are not written to
the job settings. Experiment-native outputs remain under each job directory.
SUMO network, route, and additional files named in supplied `.sumocfg` inputs are
also checked and recorded. Experiment scripts are hashed; their source is not
modified. The temporary methodology map remains under ignored `temp_content/`.
